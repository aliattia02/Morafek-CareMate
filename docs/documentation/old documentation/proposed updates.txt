Architected offline-first FHIR implementation with encrypted bundle exchange
Architected offline-first FHIR implementation with encrypted bundle exchange
Here's the full picture of how to make the mobile app genuinely local-first — the Render backend stays alive only for auth and media, while all health data never leaves the device without patient consent.



The key insight: your backend becomes an auth-only service. MongoDB keeps only the users collection. All health data lives in SQLite on the patient's device.

Phase 1 — Extend db.ts with full EHR schema

Your current db.ts only stores vitals and pending_vitals. You need to add tables for visits, conditions, exercises, documents metadata, messages, and FHIR identifiers — all the collections currently in MongoDB. The schema maps 1:1 to your existing Mongo documents, so the TypeScript types in ehr.ts don't change.

  visit_date TEXT, chief_complaint TEXT,

Phase 3 — New utility files for Plan B

fhirBundleExport.ts reads all SQLite tables and builds a FHIR R4 Bundle JSON — this is the offline equivalent of your existing GET /api/patient/fhir-export endpoint, but it never touches the network.

fhirCrypto.ts uses crypto.subtle (available on RN 0.81 via the Hermes engine's Web Crypto implementation):

ts
export async function encryptBundle(bundleJson: string) {
  const key = await crypto.subtle.generateKey(
    { name: 'AES-GCM', length: 256 }, true, ['encrypt', 'decrypt']
  );
  const iv = crypto.getRandomValues(new Uint8Array(12));
  const cipher = await crypto.subtle.encrypt(
    { name: 'AES-GCM', iv }, key,
    new TextEncoder().encode(bundleJson)
  );
  const exported = await crypto.subtle.exportKey('raw', key);
  // QR contains: base64(key) + "." + base64(iv)  — ~70 chars, fits any QR
  const qrPayload = btoa(String.fromCharCode(...new Uint8Array(exported)))
    + '.' + btoa(String.fromCharCode(...iv));
  return { cipherBytes: new Uint8Array(cipher), qrPayload };
}
fhirBundleImport.ts takes the decrypted delta bundle from the doctor and merges new Encounter, Condition, and CarePlan entries into SQLite, deduplicating by id.

Phase 4 — What to strip from the backend

All EHR route handlers in ehr_routes.py, patient_routes.py (except /api/patient/profile), and monitoring_routes.py become no-ops or can be deleted. The backend retains:

auth_routes.py — login, register, forgot/reset password, delete account
upload_routes.py — Cloudinary avatar upload (the only binary data worth a server)
metadata_route.py — the FHIR CapabilityStatement (no auth, no DB)
patient_routes.py → only /api/patient/profile (name, DOB, role — non-PHI)
MongoDB keeps only the users collection. The ehr_*, messages, clinics, patient_fhir_identifiers, and monitoring_alerts collections can be dropped entirely.

Phase 5 — DSGVO posture

The QR code contains only the symmetric key — nothing else. The encrypted file is ciphertext with no metadata. A network observer, a compromised Cloudinary account, or a subpoena to Render yields nothing about any patient's health. The decryption key physically exists only on the patient's screen for the duration of the handoff. This satisfies Art. 25 (data minimisation, privacy by design) and Art. 32 (AES-256-GCM is explicitly recognised as an adequate technical measure).

The migration order I'd suggest: extend db.ts first (no UI change), then redirect one service at a time starting with vitals (already partially cached), then implement the export/crypto utilities, and add the share screen last once the data layer is solid.
